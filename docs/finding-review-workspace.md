# Finding review workspace (#62)

The current scope covers finding triage, confidence and contradiction review. Remediation task ownership, due dates, accepted-risk expiry and retesting remain deferred by the roadmap reset. A false-positive classification does not delete evidence or establish remediation.

The finding panel filters observations by asset, tool, source severity, effective validation state and whether confidence is source-reported or unknown. Filters start at All. A persistent count highlights severe low/unknown-confidence evidence, including the count deliberately hidden by active filters. Clear filters restores all source observations. Cards retain source/evidence/run/observation references, observed time, source state, severity/CVSS version/vector, confidence method, and the separate current human decision. Source observations are not relabelled as confirmed findings.

Each card supports a reasoned reviewer decision and assessment-local contradiction selection. History shows prior classifications, reasons, reviewer identity and timestamps; the API flags when the latest-100 decision history is truncated. The existing correlation panel preserves candidate and reviewed cluster rationale, merge/split, and undo. These decisions never remove occurrences or rewrite original evidence.

Both review mutation APIs now accept `expected_revision` (default 0 for the initial empty stream). GET history returns the current revision. Under the assessment database lock, a stale revision returns 409 and records no decision. Clients must send the loaded stream revision, including after unrelated observation decisions. The UI reloads on conflict, clears obsolete selections and retains the rationale draft for a deliberate re-review. Merge/split refreshes its current revision and coverage after errors. Assessment changes remount the panel to isolate drafts and history.

Successful triage refreshes coverage/ranking. The next report freeze includes the latest decisions; existing frozen reports retain their previous contents/hash. The UI explicitly asks the analyst to create a new report snapshot. There is no automatic alteration of a downloaded report. Confidence remains uncalibrated or unknown; no unsupported probability is manufactured.

Verification: `frontend/scripts/check-triage-ui.mjs` runs actual Chromium/React interactions against synthetic review responses, covering all five filters, severe uncertainty, escaped source text, contradiction selection, reasoned false-positive decisions, history, conflict recovery and reload. Backend tests cover stale writes, original preservation and PostgreSQL review behavior; `test_triage_changes_only_new_report_snapshots` proves the report boundary. Existing correlation tests cover merge/split/undo. CI runs these alongside the existing browser and API suites. No production scanner evidence, live tool execution or measured accuracy is claimed; genuine-source final demonstration remains in its existing gate.
