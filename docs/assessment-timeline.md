# Assessment timeline and safe recovery (#58)

After sign-in and assessment selection, the timeline reconciles job snapshots, control state, audit events and reviewer decisions every five seconds. Job and audit events come from finite authenticated SSE batches. Each stream resumes with its own Last-Event-ID. Cursors advance only with successfully received records; invalid identifiers, another assessment's events or mismatched job sequences fail the refresh. Old/repeated frames cannot move the cursor backwards or duplicate cards. The UI retains up to 1,000 received audit and job events and the current 50-job API window. More than 100 pending events require multiple batches. Reload reconstructs history from zero; credentials and private history are not placed in browser storage.

When a refresh fails, the timeline keeps historical cards and labels current status unknown. Reconnect refreshes snapshots and resumes event streams without dispatching work. A stale heartbeat remains unknown even with a healthy API connection. Partial, failed, cancelled and blocked jobs show diagnostics and human recovery instructions; unknown execution requires termination/evidence reconciliation. The current API supplies no retry-eligibility decision, so the UI offers no automatic job retry. A fresh scoped request and approval are required where applicable. No estimated completion percentage or successful native execution is inferred from events.

Stop and resume call the existing backend controls. A pending or failed response never establishes success. The receipt key survives an ambiguous control failure within the panel, making a retry idempotent. A confirmed stop blocks new work but does not establish termination of running/disconnected workers. Execution claim states remain visible; resume is available only after a connected stopped snapshot, and server role/reconciliation checks still apply. Resuming does not restore approvals or submit jobs. Control epochs prevent an older in-flight snapshot from overwriting a newer confirmed control response.

Plan and finding decision records expose explicit human rationale, record/plan/observation references and contradiction references, with navigation to plan/evidence review. Audit cards use a small metadata field list and distinguish recorded imports from AI proposals; no raw evidence, request bodies, model prompts or internal reasoning are rendered. React escapes text, and common bearer/key/password/token patterns in free text are redacted as defense in depth; this is not a substitute for backend secret handling. A job status does not supply execution mode, so the UI marks it unknown rather than claiming a live scan.

## Verification

`frontend/scripts/check-timeline-ui.mjs` exercises the actual React panel in Chromium with clearly synthetic HTTP/SSE responses: duplicate replay, cursor continuity after connection failure, partial diagnostics, unknown status, stop pending/confirmed, resume, reload, denied control and secret-text redaction. It calls no scanner or target endpoint. CI runs this script with the existing setup and coverage walkthroughs. Real backend semantics are separately covered by `tests/test_job_progress.py` and `tests/test_control.py`, including replay and cancellation/reconciliation boundaries. A simulated API connection failure is not a production restart claim.
