# Bounded job scheduling — T21

Approved job admission is serialized by a shared database mutex after the assessment lock. The same lock order is used throughout; publisher/worker/finish paths never take the scheduler mutex and then another assessment lock. Current policy, scope revision, profile, target DNS pins and expiry are revalidated before a scheduling preference. Admission denial rolls back the entire request, including bucket changes and approval consumption. Human job priority is an integer 0–10; planner identities cannot submit jobs.

The current conservative ceilings are 16 held jobs globally, four per assessment, two per literal target address across assessments, one active-validation job globally and 30 admitted jobs per assessment per rolling hour. Queued, running, unknown and reset-required work hold slots. Token buckets have capacity one: four job admissions/sec globally, at most one/sec per assessment/target and never more than the current policy permits. Target aliases cannot bypass literal-address accounting. Shared target rates keep the stricter previously observed rate; raising that limit needs a deliberate operator migration, not a planner request. Server time and policy validity define scan windows. Exhausted budgets/rates return a visible rationale and consume no new approval.

Fingerprints include current policy digest, scope ID/revision, target/protocol/port/path/DNS pins, tool/template/profile/parameters, plan revision and adapter revision. Identical pending work is suppressed; the response identifies the existing job and leaves the new approval unconsumed. Only completed normalized jobs can be reused, for at most 60 seconds from original admission. Reuse preserves original capture time; it does not pretend to execute again. Current authority/scope validation still occurs. Changed profiles/targets/parameters/policy cannot reuse the old fingerprint. Unknown/partial/failed work is not a successful cache hit.

Outbox selection begins with the oldest bounded batch. Within that batch, effective priority is human priority plus one point per waiting second; stable oldest/ID tie breaks apply. A continually arriving priority-10 task cannot permanently outrank an older eligible priority-0 task. Work can still expire or be refused when demand exceeds the conservative limits; this is an explicit failure, not a promise of unlimited throughput. Batches and worker prefetch remain bounded. `scripts/dispatch_jobs.py` sends active-validation messages to `aegistrace.validation`; a later verified hosted validation worker must consume that queue at concurrency one. The diagnostic/native-blocked consumer never performs active validation.

These are **logical job-admission rates**, not claims about packets or HTTP requests generated by a native tool. T13's counters and these buckets cannot constrain a compromised binary's traffic. Kernel destination enforcement remains T14; actual per-tool packet/request rate settings, genuine native measurements, approved profiles and end-to-end runner acceptance remain T20/T14 integration gates. Consequently T21's native traffic acceptance remains partial while live execution is disabled.

`tests/test_scheduler.py` exercises duplicate approvals without consuming the new grant, changed parameter fingerprints, budget rollback, shared-target competition across three assessments, priority ageing, and real PostgreSQL suppression. Fixtures are explicitly test-only. No participant local setup is required.
