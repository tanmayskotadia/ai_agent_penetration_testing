# Managed identity and authorization — T15

Human accounts use Argon2id password hashes, 12–128 character passphrases, short-lived signed bearer sessions and a server-side session digest/expiry/revocation record. Every request checks current principal activity/epoch and, for assessment resources, live membership/role. Token claims cannot override database membership. Password rotation revokes all prior sessions; logout revokes the current session; administrators or the subject can revoke all sessions. There is no public self-registration or client-chosen actor-ID header.

Production mode requires managed sessions and HTTPS login. M02 operator-signed tokens are accepted only in explicitly non-production development/test/CI mode and may be disabled there with `ALLOW_OPERATOR_TOKENS=false`. Production rejects them even if that flag is true. `scripts/create_identity.py` bootstraps an administrator in a trusted runtime using an interactive hidden password prompt; it never passes the password in argv or prints it. Initial operator bootstrap and application TLS/proxy configuration happen at deployment, not on the participant's laptop now.

`POST /api/v1/auth/login` accepts JSON username/password and returns only the intended short-lived session credential and non-secret identity metadata, with no-store headers. It does not return password/hash, APP_SECRET, encryption keys or scanner/provider credentials. Persistent username/source throttles and a two-slot password-verification semaphore bound login attempts/Argon2 memory. Invalid users/passwords return the same error. There are no ambient authentication cookies; protected calls require an Authorization header, so cookie CSRF is not applicable. Any future cookie session must add origin/CSRF controls before enabling it.

Assessment creators receive admin membership. Administrators explicitly grant/update/revoke memberships. Analyst users can prepare inputs; reviewers/admins can review policy/derivatives and later action approvals; auditors read and cannot change scope or execute. Every private list/read/write/report-source/download checks access; cached mutation replays recheck live membership. A revoked reviewer cannot keep reviewer power from an old token. Sharing a session token does not grant access to another assessment.

Scanner, reporter and planner service identities cannot use password login and require a five-minute session bound to exactly one assessment. They never receive the application signing secret, evidence key or database owner credentials. Scanner sessions have no general API authority; future collector/run endpoints must explicitly scope their narrow actions. Reporter reads are limited to canonical findings and reviewed derivatives, not original files/tickets. Planner services may read findings and create draft plans; they cannot review scope, grant approval, manage identities, read raw evidence or execute commands. Services cannot become human reviewers through a re-signed role claim: database kind/membership prevail.

Actual scanner collector credentials and provider identity integration remain deployment/adapter work; the current service-role contract grants no imaginary scanner endpoint. Backend database login must be a private restricted application role at deployment; no browser or scanner gets direct SQL access. Provider-specific table exposure/RLS/least-privilege verification must precede deployment. No existing Supabase project has been modified by this issue.

The API has session/membership/password/account endpoints; analyst sign-in and collaboration screens remain M09 UI work. This issue does not claim SSO, MFA, password-reset email or public production readiness. Genuine password data stays out of audit records; auth mutations fingerprint credential changes with a server-keyed digest instead of storing raw values or confusing SecretStr's masked representation with request identity.

`tests/test_identity.py` runs actual Argon2 login/session storage, membership grant/revocation, auditor denial, forged actor/role rejection, production operator-token rejection, password rotation/logout, service no-self-approval/raw-download denial, expiration, login throttling and credential/exception redaction. Hosted CI repeats real PostgreSQL login/membership behavior. Other API/evidence/policy tests protect regressions. R12/R22/R26/R31/R32 receive actual server-side identity enforcement; genuine scanner/report credential deployment is separately outstanding.

Manual intervention now: none. Before deployment, an operator must inject private keys and provision the initial admin in the hosted runtime; no organizer question or participant local installation is needed for engineering acceptance.
