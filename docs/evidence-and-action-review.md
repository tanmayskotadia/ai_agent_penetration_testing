# Evidence inspector and action review (#66)

Each source observation in the finding panel opens its evidence inspector. The authenticated, non-cached `GET /api/v1/assessments/{assessment_id}/evidence/{evidence_id}/inspector` returns a versioned typed metadata contract: SHA-256, raw pointer/type, capture timestamp, run, tool/version, mode and state, and current original/derivative access availability. Supplying `observation_id` requires that exact observation to reference that evidence in the same assessment; mismatches and inaccessible records return 404. Inspector reads create an access event. Metadata never includes original bytes, encryption material or an unreviewed snippet.

Navigation fetches metadata only. Generating a redacted snippet, reviewing that derivative and downloading the private original are separate explicit actions. Snippets use the existing bounded server redactor and are displayed as inert React text; escaped markup is never installed as HTML. They represent an artifact derivative, not an exact finding excerpt. Recognized credentials are removed, while unrecognized sensitive text still requires human review. Only human reviewer/admin roles can mark a derivative reviewed; auditor viewers cannot generate or review derivatives. Viewing a derivative establishes neither vulnerability confirmation nor action approval.

Original access retains the existing assessment access check, retention window, decryption/integrity verification and short-lived subject/evidence-bound download ticket. The UI shows availability, requests a fresh ticket only after a download click, then verifies downloaded bytes against the metadata SHA-256 before saving an inert `.bin` attachment. A denied ticket, expired evidence or mismatched hash produces an error. Originals intentionally retain private source data and are never rendered inline. Availability metadata is advisory; read-time authorization remains authoritative.

The action review screen shows exact target, tool/profile, template/module, parameters, runtime, expected impact, rollback, referenced plan/revision, evidence inspectors, scope/revision, expiry, and action/parameter/policy/profile digests. The contract supplies no separate rationale field, so the screen identifies that absence and links the plan rather than inventing one. Common credential patterns in free-text action descriptions are redacted for display. The underlying server action digest remains unchanged.

Approve and deny each require an explicit confirmation for the displayed action digest. The screen re-reads the action before submitting and rejects changed parameters/digest or changed permissions. Viewer identities receive no allowed decisions. Expired/stale scope/profile actions disable approval, and backend role, policy, scope, profile, expiry and digest checks remain authoritative at decision/dispatch. Reopening or reloading records no approval. An ambiguous failure retains the receipt key; state is refreshed after errors. This screen never enqueues or consumes a grant. Approvals remain single-use and action-bound in the existing backend.

## Verification

`frontend/scripts/check-evidence-approval-ui.mjs` runs actual Chromium components with synthetic HTTP fixtures. It checks bound reference navigation, inert redacted text, explicit derivative review, denied original access, ticket headers and verified bytes, expired actions, viewer restrictions, changed parameters, and a denial carrying the exact displayed digest. No scanner endpoint is called. Existing triage browser tests verify finding cards and source references; the inspector binding is independently enforced by backend tests.

`tests/test_evidence.py` verifies observation/evidence matching, metadata without originals, outsider denial, auditor restrictions and forged tickets. Existing evidence/approval tests cover encryption/redaction, managed-role revocation, forged grants, changed parameters, stale scope, duplicate decisions, dispatch digest matching and single-use behavior. CI runs these with all UI walkthroughs. These are explicitly synthetic engineering checks, not genuine scan results or live exploitation acceptance. R04/R12/R26/R31 map to the explicit approval boundary; R09/R16/R27 map to source trace and safe failures. No new credentials, schema migration or manual setup is required.
