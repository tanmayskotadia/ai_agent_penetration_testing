# Inference, command and report boundaries — T18

Scanner banners, HTTP responses, imported text and retrieved documents are untrusted data. They cannot grant authority. The API accepts versioned, extra-field-forbidden `ReasoningProposal` records; it does not call a model. Every proposal requires assessment-owned, retained, human-reviewed evidence derivatives. Context carries original and derivative hashes, source pointers and an explicit `instructions_are_data` label. Context reads are audited with the actual human/service actor kind. Originals remain private and unchanged.

Proposals remain `ai-inference`, `suspected` or `unknown`, and `pending-human-review`. They create neither findings nor approvals. Unknown confidence stays null; supplied confidence requires a method and is not represented as calibrated. Mentioned CVE/CWE identifiers must occur in cited reviewed text. This is a consistency check, not proof that an identifier or vulnerability is valid. Action citations must be a subset of the reviewed context, and proposed actions pass current deterministic policy validation. Human approval and dispatch remain separate T16 boundaries. A planner identity can submit proposals/context, not create execution plans or approve actions.

Configured application/encryption keys and common credential patterns are masked from context and proposal display fields. Markup is escaped. Heuristic instruction flags are diagnostic only: the actual protection is the schema, ownership, retention, approval, capability and execution boundaries. Redaction is not guaranteed to detect every secret; human review and the approved-model data policy remain required. Cached context cannot bypass current retention/review checks.

The internal command builder accepts an existing human-approved claim and current worker lease, never a shell string or a model-selected executable. It rechecks assessment stop state, approval snapshot, reviewer, scope/DNS pins, runtime deadline and capability state. The sole argument template is bounded Nmap TCP-connect against literal IPv4 pins with DNS/scripts disabled. Executables must be registered by trusted configuration with absolute path, size, hash and installed version. All native capabilities remain planned, so actual command construction is denied today. The helper does not execute a process or install a tool. Executable filesystem immutability and kernel egress enforcement are runner prerequisites.

Intelligence references are constructed from fixed NVD, CVE, CWE and MITRE identifier templates. URL validation accepts only the exact canonical reference; no network request occurs. A future fetcher must separately enforce redirect, size, provenance and destination controls. Report assets accept only registered UUID-to-bytes entries, bounded to 1 MiB; URL/path inputs fail without fetching. No PDF/HTML renderer is integrated yet. A later renderer must use this boundary, disable external resource loading and undergo real rendering acceptance; this task does not establish renderer safety by itself.

`tests/test_inference_guards.py` uses expressly handcrafted adversarial fixtures: injection/exfiltration narratives, markup, invented CVE claims, unknown citations, executable fields, expired cached context, unreviewed derivatives, arbitrary report/retrieval URLs and command arguments. API tests assert no approval/finding creation, no configured-key exposure, preserved uncertainty and denial of an unverified native adapter. The service-marked case repeats the API checks against actual CI PostgreSQL. These tests are neither genuine scanner captures nor model-quality/accuracy measurements.

No participant local setup or manual input is needed for these controls. A future operator supplies valid authority/evidence at runtime; real model invocation, native tools, retrieval and report rendering remain later integration work.
