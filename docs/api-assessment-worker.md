# API assessment worker — T27 / issue #44

Issue #44 now includes the persisted authenticated workflow: definition import, encrypted credentials, reviewed exact-operation jobs, a private worker, method-level outcomes, coverage display and terminal JSON exports. The HTTP API queues reviewed work; it does not send target requests itself. Production deployment of the isolated runner remains tracked by #28.

## Definition contract

The OpenAPI 3.x parser now applies operation-level servers before path-level servers before document servers. Every declared server is included in scope checking, even when overridden. Server variables and path references are rejected rather than silently interpreted. Security alternatives retain OpenAPI OR semantics between alternatives and AND semantics within each alternative; an empty alternative permits anonymous access. Query-bearing servers remain rejected. Import normalization preserves the effective URL and original security alternatives with each operation.

## Worker contract

`aegistrace.api_assessment.assess_operations` accepts an immutable, content-hashed operation plan, an exact set of approved method/URL pairs, a callback that reloads current execution policy, a worker-owned credential provider, cancellation and a trusted transport. Even GET requires explicit approval, because a GET handler can change state. No body, query substitution, automatic login, OAuth token refresh, cookie replay, path-variable substitution or arbitrary authentication scheme execution is supported. Missing support is not inferred as success.

The default transport makes one HTTPS request to the authorized pinned IP with certificate/hostname verification, no environment proxy, no redirects and no response-body collection. It verifies the connected peer before TLS. It uses socket timeouts; the enclosing runner must also enforce a total job deadline, process isolation and kernel egress rules. One batch is sequential and spaces requests according to current policy. Global concurrent batches and policy rate reservations must be enforced by the existing durable job dispatcher; this library's spacing is not a distributed rate limiter.

Bearer/header API-key credentials are supplied only by the trusted worker provider, with an explicit HTTPS origin and expiry. They are hidden in model repr and never copied into result records. Header names and values are validated; routing/framing/proxy/cookie headers are rejected. Credentials are reloaded per operation. Each AND alternative must have every credential and nonconflicting headers. If no alternative is usable, the operation is blocked before dispatch. The provider must be scoped to the assessment and reviewed schemes; it must not expose arbitrary environment-variable lookup to a caller.

Results record method/URL, attempted state, status code, success/failure/exclusion and authentication limitations. HTTP 2xx means request success; it does not prove which identity was authenticated or establish vulnerability status. 401/403 are rejected, redirects are failed without following them, and missing/expired credentials leave the operation unattempted. Hidden/unlisted routes never count as covered. Credential and transport exception text is discarded.

## Verification

`tests/test_api_assessment.py` uses a disposable test-only FastAPI application to exercise public, protected and forbidden routes and a wrong-token request. Separate adversarial checks cover missing/expired/wrong-origin credentials, unapproved destructive methods, external destinations, cancellation, scope exclusions, modified plan digests, redirects, provider error redaction and OpenAPI server/security semantics. The disposable transport is in-process and does not establish the deployed pinned-TLS/kernel boundary.

## Integrated service and operator procedure

All paths below are under `/api/v1/assessments/{assessment_id}` and require an authenticated owning/member identity. Mutations require `X-Request-ID` and `Idempotency-Key`. An auditor cannot mutate. Review decisions require a human reviewer/admin. Secrets are never returned or included in audit payloads; mutation receipts use a keyed fingerprint to distinguish secret changes without storing them.

1. Upload and normalize an OpenAPI JSON artifact through the existing encrypted evidence/import workflow. Retain the returned normalization ID. Old definitions lacking effective URLs/auth alternatives must be reimported.
2. Create a current live-request scope and reviewed execution policy using existing scope/policy APIs. Set context and actual authorization reference at runtime. Imported definitions never grant authority. Exact HTTPS hosts/ports, DNS pins, exclusions, rates and `active-web` permission must be present.
3. POST `/api-credentials` with `kind` (`bearer` or `api-key`), `value`, exact HTTPS `origin`, future `expires_at`, and `header` for a header API key. The secret is encrypted with AES-GCM using `EVIDENCE_KEY`, the key ID and assessment/credential/origin/expiry authenticated metadata. The response contains only its ID, origin and expiry. Never enter a secret into a public issue. Rotation creates a new credential ID; revoke an old one with POST `/api-credentials/{id}/revoke`.
4. POST `/api-checks` with `normalization_id`, `policy_id`, `selected_indices` (zero-based source operations), required `expected_impact` and `reset_instructions`, optional `credential_ids` mapping declared scheme names to private credential IDs, and `max_runtime_seconds` (1–300). The only supported execution profile is `active-web`. Credentials must match the definition's supported bearer/header API-key scheme. Unselected operations remain excluded, including destructive methods. Concrete path parameters, request bodies, query keys, cookie auth and OAuth refresh are unsupported; they are not silently generated. Review binds the versioned impact-rule digest and actual policy limits; changed rules require a new request/review.
5. Review the returned full plan and digest. A human reviewer POSTs `/api-checks/{id}/decision` with `decision: approve` and that exact `digest`. `deny` terminates pending work; `cancel` cancels queued work or requests running cancellation. Consent binds the immutable source, selected operations, credentials, policy, scope epoch and deadline. It expires after at most five minutes.
6. On the **private isolated runner**, run `python -m aegistrace_workers.api_check_cli --poll`. The runner uses the shared database and privately injected application/evidence keys, not a public execution endpoint. It claims a job once, reloads policy/reviewer/stop state before dispatch, uses the shared policy rate/concurrency reservations, and supervises each HTTPS request in a killable process. A crash/deadline leaves ambiguous work `unknown`; it is not automatically replayed. A new request and review are necessary for another attempt. The one-job CLI form accepts assessment ID and check ID.
7. GET `/api-checks/{id}` or `/coverage` to inspect persisted per-method results. Coverage includes the source normalization/evidence IDs and result digest; the workspace shows these records. GET `/api-checks/{id}/export` downloads the terminal source-linked result for reviewer/report consumption, with no secrets or response bodies. It is not a full professional VAPT report.

`tests/test_api_check_workflow.py` verifies the entire HTTP intake/review/private-worker/coverage/export path, single-use execution, encrypted round trip, outsider denial, revoked credentials, stale scope, tampering, cancellation and crash reconciliation. It also runs against actual PostgreSQL in CI. `tests/test_api_check_tls.py` creates a private test-owned HTTPS service and temporary certificate, then executes the same persisted workflow with the **default** supervised pinned transport. It verifies certificate mismatch, redirect non-following and process deadline termination. These are real local HTTP requests to a disposable application, not production scan evidence. The existing egress harness independently tests kernel deny rules.

## Participant requirements

Service regressions share one disposable PostgreSQL database. Evidence verification queries must filter both assessment and evidence ID; adding another valid assessment must not change the test's expected row count. The #44 PostgreSQL workflow runs alongside the evidence, approval and job service regressions.

No manual action is required for engineering acceptance or disposable tests. No keys, local installation, licensed scanners or organizer responses were needed. To use the feature against an actual hosted API later, enter a dedicated restricted bearer/header API key through the private credential API, approve exact operations under valid authority, and deploy the private runner with verified networking (#28). Supabase/Render connection alone is not proof that the runner is deployed or isolated. Keep the general-purpose asset-owner profile distinct from any competition-specific demonstration requirements.
