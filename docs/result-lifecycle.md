# Result versions and late output — T23

Each accepted candidate normalization writes an append-only result revision in the same database transaction as its source-linked asset/service/observation snapshot. A stable input digest covers original source hash, parser revision, mapping and parser outcome. Replaying identical input reuses its revision; changed evidence/parser/mapping/outcome creates the next revision. The revision retains run and original capture time, tool mode/version, source evidence hash, normalized IDs, warnings and explicit `assessment_coverage=unknown`. Partial, failed, cancelled, blocked, and candidate-normalized are separate job/parser states; only a successful source parser outcome may say normalized. No state asserts complete assessment coverage.

Reviewers can freeze selected result revision IDs as a private deterministic JSON export. The export hashes the complete immutable payload, has a canonical report snapshot ID, and database triggers reject update/delete. Reads recheck the content hash and require assessment access. Future imports or callbacks cannot alter an existing export; a new reviewer-created export is required. The export freezes the selected source observations, assets, runs, scope revisions, reviewer context, correlation/risk explanation, findings/occurrences/decisions, approval records and coverage snapshot. A versioned VAPT content contract provides executive summary, scope/rules of engagement, methodology, assets, tool runs, source severity distribution, prioritized observations, reviewed findings, impact/remediation, approvals, unknowns and limitations. Empty or unsupported fields remain explicitly unknown. The `/result-exports/{id}/pdf` route renders these sections from the frozen content and lists observation evidence IDs alongside the source hashes and revision IDs in the manifest. It does not add inferred findings or claim full coverage, valid authorization, live testing, or a completed assessment. Real-data report review remains outstanding. Evidence retention remains governed by evidence policy/report snapshots.

A late worker callback must present the job's original worker UUID and epoch after the lease/job is no longer current. The collector stores bounded (2 MiB) bytes encrypted with job/artifact-specific AES-GCM associated data, one-hour TTL, hash/key ID and `quarantined-late` state. Duplicate identical callbacks return the same artifact ID; different callbacks do not replace one another. Unknown/current results, findings, normalized rows and prior exports remain unchanged. A reviewer may reject it, or associate the bytes with a retained evidence reference whose decrypted bytes match the exact hash. Inclusion only moves it to `reviewed-new-import-required`; it never mutates the completed run or prior export. A fresh import and full current scope/provenance checks are required. Expired quarantined bytes are purged by the bounded dispatcher retention sweep.

This is not a scanner result-quality or late-live-target acceptance claim. T14/T20 still gate native runner/collector operation, and the native worker currently returns blocked. Tests use explicitly `TEST ONLY` bytes and synthetic callbacks; they verify hashes, state fences, immutability, retention and Postgres service behavior, not genuine scanner output. No participant local setup is needed.
