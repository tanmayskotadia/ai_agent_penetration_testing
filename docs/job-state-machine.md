# Durable approved jobs — T19

`POST /api/v1/assessments/{id}/scan-jobs` takes an existing human approval ID and exact action digest. Human access, current reviewer/session, scope/policy, expiry, rates and stop state are rechecked by the T16 claim consumer. The single-use claim, job, outbox record, API receipt and audit attribution commit together. An encryption key is required before queueing. The older request-only `/jobs` API stays explicitly blocked for compatibility; it cannot bypass this route.

The trusted hosted dispatcher runs `scripts/dispatch_jobs.py` in bounded batches. It first reconciles leases/unstarted expiry and purges expired temporary output, then publishes only job IDs to Celery/Redis. Broker operations use bounded connection/socket timeouts and no implicit publish retry. Failed publication remains in the outbox with exponential delay, at most five attempts; the job explains broker unavailability. A crash after Redis accepts a message but before the database records publication can duplicate delivery. The worker locks the assessment/job and consumes its persisted claim once; duplicate messages cannot start another attempt. Operators can rerun the dispatcher after broker restoration, without reapproving or recreating an already-started scan.

`queued → running → collected | partial | failed | cancelled | blocked` describes execution/collection, not successful normalization. Workers cannot claim `completed`. The start transaction rechecks authority and reserves a five-second fenced execution lease before any external submission. Worker UUID, epoch, attempt (one), deadline and opaque external scan ID are persisted. Submission IDs must be recorded by trusted adapters; the ambiguous crash window before recording an external ID still becomes `unknown`, never a reason to resubmit. Callbacks use a heartbeat and bounded runtime; stop/cancel uses M03's execution controls. Cancellation overrides an ordinary collected outcome. Stateful termination can require reset review.

After a lease expires, reconciliation sets job and execution to `unknown`, preserves output and holds the reservation. A redelivered message does not rerun it. Existing reviewer termination/reset evidence mechanisms reconcile the execution; this does not silently change the unknown job into a success or restore its approval. New work requires a fresh approval. Unstarted expired claims release their reservation exactly once. Dispatcher batches are bounded and rotate by last reconciliation time; deployment must schedule the dispatcher/reconciler, monitor exhausted outbox attempts and preserve the database.

Trusted workers may append at most 256 chunks / 2 MiB total with the current job fence. Each chunk is AES-GCM encrypted with job/sequence AAD and records hash/key ID/size. Earlier committed chunks survive a later worker or parser failure. These are temporary collection artifacts with a one-hour TTL; the retention sweeper deletes expired bytes. They are not canonical evidence, normalized services or findings. No raw data, exceptions or broker credentials enter task arguments or public diagnostics. Key rotation must retain referenced encryption keys until private data is migrated/purged; decryption/normalization is a later collection boundary.

The actual Celery task is integrated, but currently reports `blocked: verified-native-runner-unavailable` and releases the unstarted external-work slot after confirming no external process was submitted. It does not scan a target. Native Nmap work is T20; deployed runner/network/collector acceptance is T14. The seven-tool registry remains planned, and no model/report engine is enabled. CI exercises actual PostgreSQL/outbox/Redis/Celery delivery and redelivery; handcrafted crash/output fixtures are explicitly test-only. This establishes orchestration behavior, not genuine scan accuracy or hosted lab authorization.

Late acknowledgements support redelivery, not exactly-once execution. See the [Celery task documentation](https://docs.celeryq.dev/en/stable/userguide/tasks.html); database claims and reconciliation enforce the application invariant. No participant local setup is needed. Hosted dispatcher/worker deployment and valid runtime target authority are prerequisites before enabling native jobs.
