# OWASP ZAP recorded Alerts import (T25)

## Delivered behavior

The authenticated import route accepts a user-supplied ZAP 2.x Alerts JSON document (`{"alerts": [...]}`). The version must be a concrete ZAP 2.x release string. The importer does not launch ZAP, call its API, follow links, send target requests, or start either passive or active scanning. This route imports the output of work already done in ZAP; the fact that an imported alert exists does not show whether its original source traffic was proxied, replayed, crawled, passively analyzed, or actively tested.

The bounded parser runs in the isolated parser child, rejects duplicate JSON keys and unsupported shapes, and retains ZAP `id`, `pluginId`, `alertRef`, source risk/confidence labels, source pointers, HTTP method, origin, path and safe parameter names. Query keys and the ZAP parameter label are retained without values. Normalized URLs omit query strings and fragments. Request and response headers/bodies are not copied into normalized records; the original evidence remains encrypted, source-hash linked, and available only through the evidence access controls. Every endpoint is matched against the current declared scope and exclusions; any out-of-scope entry quarantines the import. The resulting observations remain `suspected`, with no CVE, confirmed finding, calibrated probability or exploitability claim.

All committed ZAP test samples are handcrafted software tests, not genuine scanner evidence. These tests prove parser and encrypted-import behavior only.

## Live runner status

No ZAP API or Automation Framework runner is delivered in this repository. Native ZAP execution remains unavailable and the capability registry correctly remains `planned`. The versioned profile catalogue describes approval rules but does not submit ZAP work. In particular, a passive-only permission must never call an import option that sends requests or an active-scan job. ZAP Automation Framework plans can configure contexts, include/exclude paths, authentication and ordered jobs; the import job explicitly supports `sendRequests: false` by default, while setting it true sends requests and follows redirects. Do not infer runtime permission from an uploaded definition or plan.

Before a live implementation can be verified and the issue closed, the user will need to provision an isolated private ZAP runner with a pinned ZAP/add-on version, internal-only API listener, API-key secret, and network egress allowlist. Then supply a genuine version-matched Alerts export and a disposable authorized application with exact scope, exclusions, authentication method and reset instructions. The future runner must verify these inputs against the one-time action-bound approval, enforce request/time budgets, prohibit redirects outside scope, observe cancellation, store sanitized output plus encrypted original evidence, and record actual ZAP/add-on versions and run timestamps. No such inputs or runner are currently present, so we do not represent this as a working live integration.

Format/control references: [ZAP API](https://www.zaproxy.org/docs/api/), [Automation Framework](https://www.zaproxy.org/docs/desktop/addons/automation-framework/), [Automation environment, contexts, exclusions and authentication](https://www.zaproxy.org/docs/desktop/addons/automation-framework/environment/), [Automation import job and `sendRequests`](https://www.zaproxy.org/docs/desktop/addons/import-export/automation/), and [authentication guidance](https://www.zaproxy.org/docs/desktop/addons/automation-framework/authentication/). API access or a locally valid plan does not grant target authorization.
