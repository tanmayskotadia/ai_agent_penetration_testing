# Job status and progress — T24

Job status is read from the durable `scan_jobs` row. The UI never estimates completion from elapsed time, output size or a percentage. `percentage_complete` is always `null`; no scanner reports a defensible percentage for this pipeline.

The authenticated status endpoint returns the stored job state, attempt count, timestamps, latest safe diagnostic, tool version and exit code when the worker actually supplied them. A started job's duration is measured from its persisted `started` event. If its heartbeat is older than 120 seconds or its lease has expired, the response reports derived `status=unknown` and `heartbeat_stale=true` while retaining `state=running`; reconciliation later persists the unknown state. Service readiness, assessment state, scan-job state and model/inference capability are separate signals.

Job progress events are committed with the queue/worker state change in the same transaction and are append-only. `GET /scan-jobs/{job_id}/events` returns a bounded finite SSE batch. Reconnect with `Last-Event-ID` equal to the last fully processed per-job sequence; batches may repeat events, so clients deduplicate by sequence. The endpoint checks assessment membership and job ownership on every reconnect. Progress rows carry the same assessment/job IDs as canonical audit records whose resource is the job ID; the audit chain remains authoritative and progress events do not copy raw audit narratives. Free-host sleeps do not erase progress history.

Diagnostics use a fixed code-to-message allowlist. Raw stderr, command output, credentials, target values and exception text are never copied into progress events. Exit codes and tool versions are shown only when the trusted worker supplies bounded values. An unavailable runner produces an actionable blocked reason and explicitly records that no external scan was submitted. It does not simulate a successful scan or emit a fabricated version, duration, finding or percentage.

The reviewer application polls job snapshots and resumes each job's SSE cursor while it is open. On disconnect it retains the last processed cursor in memory for the active view and refreshes the canonical snapshot; it does not persist bearer credentials or event content to browser storage. A later browser session can recover from sequence zero or a caller-supplied cursor. The UI labels blocked, partial, failed, cancelled, running, queued and unknown states directly and displays stale heartbeat diagnostics. A collected job is not a completed assessment; normalization and review remain separate.

Verification uses synthetic `TEST ONLY` jobs and PostgreSQL-backed CI. It proves persistence, cursor replay, stale-heartbeat presentation, static diagnostic sanitization and display behavior. It is not evidence of live scanner operation. T14/T20 retain native-runner and genuine permitted capture acceptance; no external targets are contacted by T24.
